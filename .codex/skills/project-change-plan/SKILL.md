# 프로젝트 변경 계획

## 문서 역할

- 저장소 루트의 `project_changes.md`: 개발자가 작성한 요구사항과 작업별 참고 사항.
- 저장소 루트의 `change_planning.md`: 요구사항과 현재 저장소를 확인한 뒤 작성하는 한국어 구현 계획.
- 사용자가 `project_change`, `project_changes`, `change_planning`처럼 줄여 부르면 실제 파일명을 확인해 위 문서에 연결한다. 별칭 이름으로 새 문서를 만들지 않는다.

## 실행 조건

- 사용자가 `project_changes`를 확인하거나 읽어 달라고 요청한 작업에서만 이 흐름을 시작한다. `project_change 확인해줘`, `project_changes 확인해서 만들어줘` 같은 요청을 포함한다.
- 파일이 존재한다는 이유, 일반적인 개발 요청, `change_planning.md` 작성·수정·구현 요청만으로 `project_changes.md` 확인을 자동으로 시작하지 않는다.
- 현재 작업에서 확인 요청을 받아 `project_changes.md`의 실제 내용을 읽기 전에는 `change_planning.md`를 생성하거나 수정하지 않는다. 이전 작업의 기억, 기존 계획, 대화만으로 요구사항 문서 확인을 대신하지 않는다.
- 확인 없이 계획 작성을 요청받으면 먼저 `project_changes.md` 확인을 요청해 달라고 안내하고 계획 파일은 그대로 둔다. 현재 작업에서 이미 확인한 유효한 요구사항이 있으면 반복 요청을 받지 않고 이어서 진행한다.

## 요구사항 확인

1. 확인 요청을 받으면 `AGENTS.md`, 현재 Git 상태, `project_changes.md` 전체를 읽는다. 파일이 없으면 저장소에서 실제 파일을 먼저 찾는다.
2. 파일이 없거나 내용이 비어 있거나 제목·참고 사항만 있고 변경 요구사항이 없으면 개발자에게 `project_changes.md에 원하는 변경사항과 요구사항을 먼저 작성해 주세요. 내용을 확인한 뒤 change_planning.md에 구현 계획을 작성하겠습니다.`라고 안내한다. 요구사항을 추측해 채우거나 계획 파일을 생성·수정하지 않는다.
3. 목표, 원하는 구조, 제약, 참고 사항을 함께 확인한다. 대화에서 사용자가 수정한 지시를 우선 적용하되, 문서의 실제 내용을 읽는 절차를 생략하지 않는다.
4. 유효한 요구사항을 확인한 뒤 `change_planning.md`가 있으면 읽어 현재 요구사항과 일치하는지 확인한다. 관련 소스와 도메인 스킬을 확인해 이미 구현된 부분과 필요한 변경을 구분한다.
5. 구현 방향을 바꾸는 중요한 미결정 사항은 `AGENTS.md`에 따라 세 가지 선택지와 하나의 `(Recommended)`를 제시하고 선택을 기다린다. 이미 정해진 범위의 작업을 반복 승인받지 않는다.

## 구현 계획 기록

- **사용자의 확인 요청을 받아 현재 작업의 `project_changes.md`를 실제로 읽고 유효한 요구사항을 확인한 뒤에만** `change_planning.md`에 구현 계획을 작성한다. 확인 전에는 계획 초안이나 빈 계획 틀도 파일에 기록하지 않는다.
- 파일이 없으면 생성하고, 기존 파일에서는 현재 요청에 해당하는 계획을 갱신하면서 다른 작업의 내용은 보존한다.
- 계획에는 날짜와 목적, 확인한 요구사항 요약, 변경할 파일/영역, 구현 순서, 검증 방법, 가정과 남은 사용자 결정을 포함한다. API/DTO, 영속성 및 마이그레이션, 설정, 보안 영향은 해당되는 경우에만 구체화한다.
- 검증은 변경에 맞게 선택한다. C# 변경은 빌드와 관련 테스트, 엔드포인트 변경은 스모크 테스트, 스킬/문서 변경은 형식·참조·diff 검사를 계획한다.
- 확인 후에는 계획 작성까지 진행하고, 구현도 요청받았다면 기록한 계획에 따라 관련 도메인 스킬을 적용해 구현과 검증까지 진행한다. 사용자가 검토 결과만 요청했거나 계획 기록을 생략하라고 명시한 경우에는 그 범위를 따른다.
- 실제 Plan 모드나 읽기 전용 역할처럼 파일 수정이 제한된 환경에서는 확인한 요구사항에 근거한 계획을 응답으로 전달한다. 파일 기록은 쓰기가 허용된 실행 단계 또는 담당 세션에서 수행하며, 저장하지 않은 계획을 저장했다고 보고하지 않는다.

계획은 작업 규모에 맞춰 간결하게 작성한다. 다음 항목을 기준으로 삼을 수 있다.

```markdown
# 변경 구현 계획

## 날짜와 목적

## 확인한 요구사항과 범위

## 변경 영역과 구현 순서

## 검증 방법

## 가정과 남은 결정
```

## 작업별 예외와 커밋

- 현재 요청에 `change_planning` 작성이 불필요하다고 명시되어 있으면 이번 작업의 계획 파일 생성·수정을 생략한다. 이 예외를 이후 작업의 기본 규칙으로 바꾸지 않는다.
- `project_changes.md`는 개발자의 요구사항 원문으로 유지한다. 문서 수정 요청이 없으면 계획이나 완료 보고로 덮어쓰지 않는다.
- 커밋을 수행할 때는 현재 요청에 지정된 이슈 번호를 [commit 스킬](../commit/SKILL.md)의 본문 형식에 맞춰 사용한다. 특정 이슈 번호를 공통 기본값으로 고정하지 않는다. 커밋 형식 지시만으로 커밋이나 push 요청이 있었다고 간주하지 않는다.
- 구현 중 요구사항이나 중요한 결정이 바뀌면 변경된 요구사항을 확인한 뒤 관련 계획을 갱신한다. 계획 작성 생략 지시가 있는 작업은 해당 예외를 유지한다.
- 작업 완료 후 `AGENTS.md`의 변경 요약 규칙에 따라 실제 변경, 검증 결과, 남은 결정을 `.codex/change-summaries/CHANGE_SUMMARY.md`에 기록한다.
